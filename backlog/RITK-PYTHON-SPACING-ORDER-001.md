## RITK-PYTHON-SPACING-ORDER-001 — State each Python spacing/origin parameter's axis order and make generator metadata match its output — done
- outcome: Every Python entry point that accepts a spacing/origin triple states its axis order on the parameter, and every source generator returns an image whose metadata reproduces the index-to-physical map its core produced.
- acceptance: `source_geometry_reproduces_the_core_index_to_physical_map` passes over all 24 voxels of a `[2, 3, 4]` image; the ITK-parity generators' docstrings state sitk `(x, y, z)`; `Image`/`Parcellation` state `(z, y, x)` (`image.pyi`, `connectome.pyi`).
- scope: crates/ritk-python/src/{image.rs,color.rs}, crates/ritk-python/src/filter/transform/sources.rs, crates/ritk-python/src/filter/spatial/resample.rs
- next: Resolved. The public surface carries **two documented orders**, each correct in its own family. `Image(array, spacing=…)` and `Parcellation(…, spacing=…)` use `(z, y, x)` — outermost axis first, the order `to_numpy()`'s `[Z, Y, X]` array reports — stated in `image.pyi` (`Z×Y×X`) and `connectome.pyi` (`outermost-axis first — the same order an Image reports`). The ITK-parity generators `gaussian_image_source`, `grid_image_source`, `gabor_image_source`, and `physical_point_image_source` take every tuple in sitk `(x, y, z)`, matching the `sitk.*Source` they mirror; this is stated in their Rust docstrings and pinned by `test_cmake_physical_point_image_source`, which is bit-exact against `sitk.PhysicalPointSource` with anisotropic `spacing = [0.5, 0.7, 0.9]` and therefore *does* discriminate the spacing order (the earlier note that every spacing-bearing case is isotropic or default was wrong). The real defect was not the parameter order but the **metadata** the four generators attached to their output: all four built `Point::new([origin.2, origin.1, origin.0])` (a reversed origin) and three built `Direction::identity()` (`color.rs` already used `numpy_array_direction()`). A reversed `Point` claims the first voxel sits at `(o_z, o_y, o_x)`, and an identity direction makes tensor axis 0 (depth) advance physical X, while the core returns a `[Z, Y, X]` buffer whose axis 0 is Z — so the returned image's index-to-physical map was transposed against its own data. `Spacing::new([spacing.2, spacing.1, spacing.0])` was already the correct reversal. Fixed with one SSOT, `image::source_geometry(origin_xyz, spacing_xyz) -> (Point<3>, Spacing<3>, Direction<3>)` = `(Point::new([ox, oy, oz]), Spacing::new([sz, sy, sx]), numpy_array_direction())`, now the only place the four generators build metadata; `resample.rs` (parameters named `spacing_z/y/x`, no reversal) and `image.rs`'s own constructor were already correct and are unchanged. The defect survived because the sitk parity tests compare voxel *values* — which the core computes correctly — and never read the returned `.origin`/`.direction`, and because a self-consistent transposition is invisible to any round trip. Oracle: `source_geometry_reproduces_the_core_index_to_physical_map` asserts, over all 24 voxels of a `[2, 3, 4]` image built from sitk `origin = (1, 2, 3)`, `spacing = (0.5, 0.7, 0.9)`, that voxel `(kz, ky, kx)` sits at `(1 + 0.5·kx, 2 + 0.7·ky, 3 + 0.9·kz)`. Falsified by reverting `source_geometry` to the pre-fix form: `panicked at crates\ritk-python\src\image.rs:327:21: physical X … is 3, expected 1`.
